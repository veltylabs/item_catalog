# Plan — item_catalog: the specialty belongs to the form

This module is the reference for every screen of the platform (master plan `UI_CONSISTENCY` in
`webtyp/docs`, decisions D5, D6, D10, D15): what a module stores is a form field; nothing is drawn
beside the screen title.

## Problem

The "Servicios" screen shows a specialty `<select>` next to the title (crudview `Context`), but the
specialty is not a filter: it is the `specialty_id` **of the item being saved**. Because the form does
not have that field (`specialty_id` is `model.Text()`, no widget), `ui/browser.go` wraps the presenter
in `requireSpecialty` to inject the picker's value on every save, and `ui/specialtypicker.go` loads and
draws its own `<select>`. A wrapper that patches what the form should carry is the defect.

Also, the form shows field names ("Name", "sku") because no field declares `Label`.

## Stage 1 — model (`model.go`)

1. `CatalogItemModel.specialty_id`: `Type: input.Select()` (keep `Ref`, `DB`, `NotNull`), and
   `Label: "Specialty"`.
2. Add `Label` (English; translated through `lang.json`) to every field that has a widget:

| Model | Field → Label |
|---|---|
| `SpecialtyModel` | prefix → "Prefix", slug → "Slug", name → "Name", description → "Description", is_published → "Published" |
| `CatalogItemModel` | specialty_id → "Specialty", sku → "SKU", name → "Name", description → "Description", type → "Type", price → "Price", currency → "Currency", is_active → "Active" |
| `AgreementModel` | insurer → "Insurer", code → "Code", price → "Price", is_active → "Active" |

Fields typed `model.Text()`, `model.Int()`, `BaseInt_FieldInt`, `BaseBool_FieldBool` have no widget:
no Label. Do not hand-edit `model_orm.go`; if `ormc` must regenerate it, run it as the repo's
README says.

## Stage 2 — view (`ui/browser.go`, `ui/specialtypicker.go`)

1. Delete `requireSpecialty` and all its methods and `var _` assertions; pass
   `itemcatalog.NewView(caller)` directly as the items `Presenter`.
2. Delete `Context: picker.render(...)` from the items `crudview.Config`.
3. Load the specialties once and hand them to the form:
   `itemsView.SetOptions("specialty_id", opts...)` with one `fmt.KeyValue{Key: s.Id, Value: s.Name}` per
   specialty, from `itemcatalog.OpListSpecialties` (the same call `specialtyPicker.load` makes today).
   Reload the options after the specialties view saves or deletes a specialty, if crudview exposes a
   hook for it; if it does not, load once on `Activate` of the items module and write that in the PR.
4. Delete `ui/specialtypicker.go` (no other user: `grep -rn specialtyPicker .`).
5. `tenant_id` on save: `requireSpecialty` was the only place setting it. Set `TenantId: tenantID` in the
   items `crudview.Config.NewRecord` func (beside `Type`, `Currency`, `IsActive`), never in a wrapper.

## Stage 3 — translations

Run `langc sync .`; fill the Spanish of every new key in `lang.json`: Specialty → Especialidad,
Prefix → Prefijo, Slug → Slug, Name → Nombre, Description → Descripción, Published → Publicada,
SKU → SKU, Type → Tipo, Price → Precio, Currency → Moneda, Active → Activo, Insurer → Aseguradora,
Code → Código. The three `requireSpecialty: …` keys disappear.

## Stage 4 — tests (behaviour only)

- Saving an item through the real view stack with a specialty chosen in the form stores that
  `specialty_id` (extend the existing view test; the presenter is the real one over the test
  backend, as `tests/item_catalog_view_test.go` does).
- Saving without a specialty fails validation (`specialty_id` is `NotNull`) and nothing is stored.
- Delete tests of `requireSpecialty` / `specialtyPicker` if any.

## Stage 5 — docs

`README.md`, `docs/ARCHITECTURE.md`: the specialty is a form field loaded with `SetOptions`; no
picker beside the title.
